# NPCortex v0.8.2-alpha — Leaf Affordance Recovery Fix 2

This incremental experimental patch applies to **v0.8.2-alpha AgentRecoveryFix1**.
It does not change the published version number, Character Packs, SQLite,
inventory semantics, task budgets or Minecraft safety authority.

## Why

Manual Minecraft screenshots show that Yui harvested/stored 3 oak logs in a
whole-tree task but paused at `treeRemaining=3`, `failures=5/8`, `stalls=3/5`,
with `chosen=clear_leaf(b0)` and the final result `no verified natural
occluding leaf`. A status of `leafClearable=3` is a **count across observed
block targets**, not a guarantee that a selected `b0` is currently actionable.
The old Java observation also checked sightlines from hypothetical nearby
standing positions, so it could report a leaf obstruction that did not block
the NPC's current interaction, even when a log was already visible.

## Changes

- `oakObstruction` and natural-leaf selection now describe actual obstruction
  on the **current NPC eye-to-log ray**, not hypothetical alternate rays.
  Visible/in-reach logs report no actionable leaf obstruction.
- `clear_leaf` is a bounded server skill, still checking every actual block;
  if a log is already visible/reachable the action reports unchanged instead
  of claiming that a leaf was removed.
- Backend exposes `candidate_refs_by_skill` from the live observation to
  Qwen: `mine`, `approach`, `clear_leaf`, `clear_soft`, `climb` and
  `approach_drop` have **different eligible references**. The Qwen model still
  decides which skill and reference to select; Java does NOT impose an order.
- Backend rejects inapplicable tool/ref pairs, fabricated refs, or skill
  requests outside the budgets. Forge still revalidates reach, ownership,
  collision, real block type and all modifications.
- `climb` remains a Qwen-selected option when a committed target is out of
  reach and NPC has permitted scaffold materials. This change does not
  guarantee that a particular pillar can be built.

## Important limits

- Minecraft does not expose guaranteed provenance for naturally generated
  trees; the existing conservative whole-tree checks remain in force.
- Removing speculative leaf-clear affordances makes the planner more honest,
  but it may still lack a safe traversal path to a high tree. A failed tool is
  not automatically retried in the backend; each Qwen request uses a budget.
- No creative flight, teleport, arbitrary block editing or completion claims
  from Qwen are introduced. Existing owner/world-edit validation is unchanged.
- Observation and tool selection are not proof of real world success.

## Upgrade

Stop the backend and Minecraft. Extract the Update Only ZIP and run the
included installer **from the extracted folder**:

```powershell
& "$env:TEMP\NPCortexLeafRecoveryFix2\scripts\install-leaf-recovery-v082.ps1" -ProjectRoot 'F:\AI\NPCortex'
cd F:\AI\NPCortex
.\scripts\test-v082.ps1
.\scripts\build-agentic-v085.ps1 -SkipTests
```

Start the backend again, then use `.\scripts\dev-forge.ps1 -Task runClient`.
Cancel a previous paused task (which may already have used budget), and start
a fresh natural-Oak task. Items collected previously remain in the NPC bag.

## In-game acceptance tests

1. Visible low log: the planner should prefer valid, grounded `mine(bN)`;
   it must not have an actionable `clear_leaf` for this **same** visible log.
2. Leaf on CURRENT sightline: Qwen may choose `clear_leaf(bN)` if the leaf is
   within range. Check whether the server actually confirms removed leaves.
3. Remaining higher log: verify the `climb(bN)` option is selected by Qwen
   when suitable and that the real scaffold can be built with **NPC bag**
   materials. It may still fail safely; record `chosen`, `last`, `scaffold`,
   `treeRemaining` and any pause reason.
4. Whole-tree: verify `treeRemaining=0`, `mined` drops are actually stored,
   temporary blocks cleaned and no unrelated trees edited before claiming
   complete. Repeat on small and tall natural trees.
