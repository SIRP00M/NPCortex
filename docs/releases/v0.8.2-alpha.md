# NPCortex v0.8.2-alpha — Autonomous World Interaction & Whole-Tree Harvesting

This is an **experimental source release** built incrementally from the public
v0.8.1-alpha (not a new project). Minecraft 1.20.1 / Forge 47.4.10 / Java 17;
Python Backend + local Ollama / Qwen 3 8B. This document intentionally separates
source implementation and automated tests from *unverified* in-game behavior.

## Task semantics

`/npcortex task gather minecraft:oak_log 6` now means:

1. Qwen selects a log on a natural Oak candidate and the server verifies its
   bounded whole-tree snapshot **before** the first successful mine.
2. Until that tree's original logs are all removed, Qwen selects next grounded
   skills based on the latest server observation and feedback; no Java-scripted
   action sequence. The server filters target refs to the committed tree.
3. If at least six logs were requested but the committed tree has eight logs,
   **all eight** must be harvested and inventoried. If the tree yielded only four,
   another natural tree can be selected (up to the safety caps).
4. Items stay in the NPC's own inventory, not the player's. Completion requires
   bag delta >= requested, bag delta >= mined count, zero remaining committed
   log blocks, no task-owned scaffold and zero recorded terrain edits.
5. If any requirement cannot be met within the safety budgets, pause and expose
   the precise status. Do not claim success; existing collected inventory stays.

**Important:** NPCortex cannot reliably determine whether arbitrary Minecraft
logs were manually placed. Candidate recognition requires a dirt/grass-rooted
three-log vertical Oak trunk, adjacent natural/nonpersistent oak canopy, one
unambiguous base, loaded chunks, and a bounded connected log cluster. This is
conservative *risk reduction*, not a source-of-truth natural provenance check.
Hand-placed standalone log testing for the v0.8.1 pilot is no longer valid for
whole-tree verification.

## World affordances and AI tools

Server-side observations include candidate logs with ephemeral `bN` refs,
reach, visibility, `obstruction`, `leaf_clearable`, `soft_clearable`, as well as
`tree={active,remaining,size,completed,terrain_edits}`, drop refs and proximity,
NPC bag/tools and prior feedback. Qwen can choose valid grounded actions only:

- `approach(bN)`, `mine(bN)`, `clear_leaf(bN)`, `clear_soft(bN)`
- `climb(bN)`, `descend`, `restore`
- `approach_drop(dN)`, `pickup`, `wait`, `pause`, `finish`

Java ALWAYS revalidates owner, loaded chunks, position/range, block type,
world-edit configuration and real execution results. `clear_soft` can destroy
only one visible dirt or grass block directly on a ray to a committed tree log,
maximum two recorded edits. No tools execute arbitrary coordinates or commands.
`restore` (or safe cancellation cleanup) reconstructs only the originally
recorded soil when the location remains air and contains no entity. Unsafe
restoration **pauses** for manual action, never overwrites another block.

After an NPC has mined logs, Java checks the nearby 1.5-block pickup radius
approximately every five server ticks and transfers matching oak logs to its
inventory, up to the count mined but not yet accounted for in the bag. Qwen
still chooses a route to distant drops. There is no client-side magnet animation.
Vanilla drops and preexisting logs are not individually provenance-tagged in
this release; matching is by item type/count and proximity.

## Safety caps

| Constraint | Value |
| --- | ---: |
| Min requested logs | 1 |
| Max requested logs | 16 |
| Max committed natural Oak log cluster | 32 |
| Max mined logs per task | 64 |
| Max committed trees per task | 4 |
| Max reversible soil edits | 2 |
| Qwen decisions per task | 80 |
| Consecutive no-progress actions | 5 |
| Failures | 8 |
| Task lifetime | 24,000 server ticks |

Owner/Singleplayer/Cheats/World Edits restrictions remain enabled and cannot be
removed via the model. Per-NPC task ID and in-flight request nonce prevent late
LLM responses from restarting canceled jobs. SQLite and Character Pack folders
are unchanged. Legacy actions and UI remain untouched.

## Manual acceptance tests — **NOT YET VERIFIED FOR v0.8.2**

Back up your world, enable explicit world edits, run the backend and the Forge
Dev Client. Spawn Yui near an **actual grown Oak tree**, not a placed 1-log
block, keep your player far enough from drops not to steal them, and run:

```mcfunction
/npcortex task cancel
/npcortex task gather minecraft:oak_log 1
/npcortex task status
/npcortex inventory
```

1. **Whole tree overharvest:** a natural tree with 5 logs, requested 1; expect
   `mined=5`, `stored=5/1`, `treesDone=1`, `treeRemaining=0` and COMPLETE.
2. **Two trees:** ask for 6 when first tree holds 4, second 5; expect nine logs
   (actual totals depend on trees) and no partially cut second tree.
3. **Leaf obstruction:** first retry leaf-obscured Oak; check if `clear_leaf`
   was selected, if navigation improved, and whether logs were left.
4. **Soft obstruction:** choose a naturally exposed dirt obstruction to a
   committed trunk log; check whether `clear_soft` occurs only with approved
   geometry, followed by `restore` of the recorded hole.
5. **Pickup:** verify that after close-range mining log items enter the NPC bag
   without an extra Qwen `pickup` call. Verify no auto-delivery to player.
6. **Pause/Resume/Cancel:** test cancel during movement and late Qwen response,
   pause on unreachable terrain, and safe temporary scaffold/dirt cleanup.
7. **Negative safety:** manually placed log blocks, joined tree structures,
   full inventory, insufficient materials, permission disabled, unload/chunk
   edge and owner moving far away; expect blocked/paused, no invented success.

To inspect evidence, include both Backend Console and Forge/game logs; HTTP 200
alone does not prove success. `/npcortex task status` now also prints
`treeRemaining`, `treesDone`, `terrainEdits`, `leafClearable`, `observedDrops`
and `pickupReady`.
